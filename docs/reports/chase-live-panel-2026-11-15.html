THREAT INTELLIGENCE REPORT | PHISHING CAMPAIGN ANALYSIS

Chase live-panel phishing operation rotating DuckDNS hostnames

One operator, one dedicated server, real-time capture of passwords and one-time codes

Reporter: Rishika Desai   |   Date: 15 November 2026   |   Classification: TLP:CLEAR   |   Report ID: CTI-P4-2026-11-001

Prepared for SOCRadar as part of a Senior CTI Ops Engineer candidate project. Not an official SOCRadar publication. Indicators are defanged.

Executive summary

A single operator is running a Chase phishing kit that captures usernames, passwords and SMS one-time codes in real time, and can request a second code on demand. The operator serves byte-identical pages from one dedicated server and moves to a new DuckDNS hostname each day. Because the kit relays codes while the victim waits, SMS-based verification does not protect a victim who completes the flow.

We recommend blocking the server address and the hostname pattern at web gateways, filing abuse reports with DuckDNS and the hosting provider, and hunting for the kit's file names (login[.]php, wait[.]php) in proxy logs. Details and indicators follow.

How the kit works

The page imitates the Chase Online sign-in. Analysis of the page code shows a four-stage flow controlled from the server:

  1. The victim enters a username. It is posted to login[.]php immediately, before the password, which lets the operator start a real sign-in in parallel.
  2. The victim enters a password, which is posted at once.
  3. The page asks for "the code we sent to the phone number ending in 45". The six-digit code is posted to login[.]php.
  4. The victim waits on a holding screen that polls wait[.]php every 1.8 seconds. The operator can trigger a request for a second code (typically used to approve a new device or a payment), and later release the victim to a redirect address of the operator's choosing. Without a release, the page returns the victim to the start after 9 minutes.

This is a live panel: a person, or a script watching the panel, acts on each victim's data while the victim is still on the page.

Related activity, not linked

Two other Chase lookalikes surfaced during the same pivot. They use different code and different hosting, so we track them separately.

  • securedchase[.]com (seen 14 Nov 2026, 22:57 UTC). A seven-step identity harvest: account and routing numbers, sign-in, name, contact details, email and Social Security number, posted to capture[.]php behind a fake "Checking your browser" screen.
  • reset-chase[.]com (seen 27 and 28 Oct 2026). Same page title. The two observations returned different pages, and neither matched either kit, so the link is not established yet.

Impact

  • Customers: a victim who completes the flow gives the operator a working password and a valid one-time code during the same minute, which is enough for account takeover and, with the second code, approval of a new device or payment.
  • The bank: fraud losses and customer reimbursement, plus support load from compromised accounts. Customers who rely on SMS codes are not protected against this kit.

Recommendations

For the bank and its brand-protection team

  • Report both hostnames to DuckDNS and the server address to RouterHosting's abuse desk, with the indicators in this report.
  • Watch for the next rotated hostname with the queries above, checked at least daily.
  • Move customers who use SMS codes toward app-based or passkey sign-in, and tell them the bank never asks for a code on a page reached from a link.

For SOC and fraud teams

  • Block 104.194.139[.]2 and the two hostnames at web and mail gateways.
  • Hunt proxy logs for the login[.]php and wait[.]php pattern described above.
  • Flag Chase sessions that start with a new device right after a one-time code was sent, for fraud review.
